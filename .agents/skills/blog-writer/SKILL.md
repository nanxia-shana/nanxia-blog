# 博客文章撰写技能

## 项目概述
这是为「南夏的博客」设计的文章撰写辅助技能，帮助快速生成结构完整、语气自然的技术博客文章。

### 核心特性
- 智能大纲生成: 根据主题自动生成文章结构
- 平实语气: 用真实、自然的个人口吻写作，避免夸张、做作的表达
- 迭代修改: 支持分段修改、润色、扩写
- 博客风格: 符合个人博客的分享式风格
- 主题聚焦：不追求面面俱到，只写与主题直接相关的内容，避免发散式科普和堆砌背景知识
- 克制输出：保持内容密度的同时懂得”收住”，宁可留白也不注水，让每段话都有存在的理由
- 个人印记：开场白和结尾语适当口语化，穿插真实的个人经历和观点输出，让文章读起来像”南夏本人写的”而不是”模板生成的”
- 图片留白：涉及需要图片说明的内容，用 `[此处贴图：图片类型描述]` 格式标注；流程图可用文字代码块模拟绘制
- 标题序号：一级（H2）标题统一添加序号格式：`1. `、`2. ` 等，序号后紧跟一个空格

### 南夏专属风格规范
**用词偏好：**
- 用”东西”代替”玩意儿”
- 用”弄明白”代替”搞懂”
- 用”理解”代替”头大”
- 避免过于网络化的表达，保持平实、真诚的语气

**开头风格：**
- 直接切入，避免”说出来你可能不信”这类过于戏剧化的开场白
- 用”刚从 JS 转到 TS 的时候，我看到...”这样的平实叙述方式
- 标题简洁，不添加过多情绪化修饰词

## 文章结构规范

### 标准博客结构
```
1. 开篇引入
   - 为什么写这篇文章
   - 个人经历/背景故事
   - 读者能学到什么

2. 主体内容（分章节）
   - 概念解释（用生活化比喻）
   - 步骤讲解
   - 代码示例 + 注释
   - 踩坑经验分享
   - 个人理解和感悟

3. 总结
   - 核心要点回顾
   - 下一步学习建议
   - 互动提问（鼓励评论）
```

### 语气风格规范
**个人印记使用原则:**
- **开场白和结尾**可以适当口语化，用真实的个人经历引入，比如"说出来你可能不信..."、"这个坑我当年踩过..."
- **主体内容**保持专业平实，技术描述准确清晰
- **踩坑经验**可以适度吐槽，比如"别问我怎么知道的"、"说多了都是泪"，点到即止
- **结尾互动**可以亲切一些，比如"大家一起早点下班"

**推荐写法:**
- 个人经验以踩坑记录、使用心得的形式呈现
- 内容以实用性为导向，每个技巧说明"是什么、怎么用、什么时候用"

**避免写法:**
- "本文将深入探讨..."等过于正式的学术化表达
- "太香了"、"yyds"等过于网络化的口语
- 主体内容过于随意，影响技术内容的专业性

### 图片处理规范
**图片留白格式:**
```
[此处贴图：具体图片类型描述]
```
示例：
- `[此处贴图：Chrome DevTools Sources 面板截图]`
- `[此处贴图：右键请求展示 Copy as cURL 选项的截图]`

**流程图文字模拟:**
对于流程类内容，用代码块绘制文字流程图：
```
步骤1 → 步骤2 → 步骤3
           ↓
         步骤4
```

## VitePress 格式规范

### 禁用项
- **不使用 `[[toc]]`** — VitePress 自带右侧目录导航功能
- **文章正文中不使用 emoji** — 保持专业、简洁的排版风格
- **不使用 `---` 作为章节分割线** — VitePress 标题前换行自动会出现分割线，无需手动添加

### 自定义容器
使用 VitePress 自带的自定义容器标注提示、警告等内容：

```markdown
::: info
这是信息框，用于说明一般性内容
:::

::: tip 小提示
这是提示框，用于给出建议和技巧
:::

::: warning 注意
这是警告框，用于提醒注意事项
:::

::: danger 踩坑提醒
这是危险警告框，用于标注容易出错的关键点
:::

::: details 点击展开详情
这是折叠块，用于隐藏较长的内容（如代码示例）
:::
```

### GitHub 风格警报（可选）
也支持使用 GitHub 风格的警报标注：

```markdown
> [!NOTE]
> 强调用户在快速浏览文档时也不应忽略的重要信息。

> [!TIP]
> 有助于用户更顺利达成目标的建议性信息。

> [!IMPORTANT]
> 对用户达成目标至关重要的信息。

> [!WARNING]
> 因为可能存在风险，所以需要用户立即关注的关键内容。

> [!CAUTION]
> 行为可能带来的负面影响。
```

### 代码块高级格式

**行高亮**

使用 `{行号}` 标记高亮行：
```markdown
```js{4}
export default {
  data () {
    return {
      msg: 'Highlighted!'
    }
  }
}
```

支持多种形式：
- 单行：`{4}`
- 多行：`{5-8}`、`{3-10}`
- 多个单行：`{4,7,9}`
- 混合：`{4,7-13,16,23-27,40}`

也可以使用注释标记高亮：
```markdown
```js
export default {
  data () {
    return {
      msg: 'Highlighted!' // [!code highlight]
    }
  }
}
```

**代码聚焦**

使用 `// [!code focus]` 注释聚焦某一行并模糊其他部分：
```markdown
```js
export default {
  data () {
    return {
      msg: 'Focused!' // [!code focus]
    }
  }
}
```

支持聚焦多行：`// [!code focus:3]`（聚焦当前行及后续2行）

**代码差异对比**

使用 `// [!code --]` 和 `// [!code ++]` 标记增删代码：
```markdown
```js
export default {
  data () {
    return {
      msg: 'Removed' // [!code --]
      msg: 'Added' // [!code ++]
    }
  }
}
```

**错误与警告标记**

使用 `// [!code warning]` 和 `// [!code error]` 标记：
```markdown
```js
export default {
  data () {
    return {
      msg: 'Error', // [!code error]
      msg: 'Warning' // [!code warning]
    }
  }
}
```

**行号控制**

```markdown
```ts {1}
// 默认禁用行号
const line2 = 'This is line 2'
```

```ts:line-numbers {1}
// 启用行号
const line2 = 'This is line 2'
```

```ts:line-numbers=2 {1}
// 行号已启用，并从 2 开始
const line3 = 'This is line 3'
```

**代码组**

使用 `::: code-group` 对多个代码块分组展示：
```markdown
::: code-group

```js [config.js]
/**
 * @type {import('vitepress').UserConfig}
 */
const config = {
  // ...
}

export default config
```

```ts [config.ts]
import type { UserConfig } from 'vitepress'

const config: UserConfig = {
  // ...
}

export default config
```

:::
```

## 工作流程

### 1. 创建新文章
**第一步: 生成大纲**
```
输入: 文章主题 + 可选的个人背景/经历
输出: 完整的文章大纲，包含：
  - 文章标题（3个备选）
  - 章节结构（每章简要说明）
  - 预估字数
  - 重点提示
```

**第二步: 分段撰写**
- 每写完一段，让用户确认是否满意
- 根据反馈调整语气、增删内容
- 代码示例要带详细说明

**第三步: 整体润色**
- 检查段落过渡是否自然
- 优化开头和结尾
- 添加过渡句，让文章更连贯

**第四步: 数据同步（重要）**
文章撰写完成后，自动完成以下工作：
1. **确定分类路径**: 根据文章内容确定大分类（前端/后端/杂项）和子分类
   - 前端子分类：`base`（基础）、`engi`（工程化）
   - 后端子分类：`base`（基础）、`nodejs`、`database`（数据库）、`architecture`（架构）
   - 杂项子分类：直接放在 `misc` 下
2. **写入文件**: 将文章保存到正确路径 `docs/knowledge/[大分类]/[子分类]/[文件名].md`
3. **更新 knowledgeData.ts**: 将文章信息添加到 `docs/.vitepress/data/knowledgeData.ts` 对应数组中
4. **更新 utils.ts**: 将文章菜单添加到 `docs/.vitepress/utils.ts` 的 `menuList` 对应分类下

### 2. 修改现有文章
支持以下修改类型:
- **润色**: 优化表达，让语气更自然
- **扩写**: 展开某个章节，增加细节
- **缩写**: 精简冗余内容
- **调整结构**: 调换段落顺序
- **添加示例**: 补充代码/案例
- **修改标题**: 优化标题吸引力

### 3. 特殊内容处理

**代码示例规范:**
```markdown
```typescript
// 代码前要有自然的引入语
// 代码中要有详细注释
// 代码后要有讲解说明
const example = () => {
  // 这里做什么
  return result;
};
```

::: tip 小提示
这段代码的关键是...
:::
```

**踩坑/经验分享格式:**
```markdown
::: danger 踩坑提醒
这里我当时卡了好久，主要是因为...
后来发现解决办法其实很简单：...
:::
```

**个人感悟格式:**
```markdown
## 写在最后

其实技术这东西吧，...
我觉得最重要的不是...而是...
希望这篇文章能帮到你~
```

## 使用示例

### 示例 1: 从零开始写文章
```
用户: "帮我写一篇关于 Vue3 Composition API 的文章，我刚从 Vue2 转过来，踩了不少坑"

技能输出流程:
1. 生成大纲（标题备选 + 章节结构）
2. 用户确认大纲
3. 分段撰写（开篇 → 主体 → 踩坑分享 → 总结）
4. 逐段确认修改
5. 生成完整 Markdown 文件
```

### 示例 2: 修改现有文章
```
用户: "帮我把这篇文章的第三章改得更口语化一点，太生硬了"

技能输出:
1. 提取目标段落
2. 重写（保留技术要点，换表达方式）
3. 对比展示修改前后
4. 根据反馈微调
```

### 示例 3: 添加内容
```
用户: "给这篇文章加一个关于 XXX 的踩坑分享，我当时因为 XXX 浪费了 2 小时"

技能输出:
1. 设计合适的插入位置
2. 撰写踩坑段落，使用 VitePress 自定义容器
3. 确保与上下文衔接自然
```

## 文章文件规范

### 文件位置
```
docs/knowledge/[大分类(前端/后端/其它)]/[子分类]/[文章名].md
```

### Frontmatter 格式
```markdown
---
layout: doc

lastUpdated: false
title: 文章标题
description: 简短描述（用于 SEO 和预览）
category: 分类名
date: YYYY-MM-DD
cover: 可选封面图路径
---
```

## 质量检查清单

每篇文章完成后自动检查:
- [ ] 开头有清晰的背景引入，说明文章价值
- [ ] 语气平实自然，专业但不生硬
- [ ] 有适度的踩坑/经验分享（0-2个为宜）
- [ ] 代码示例有注释和必要说明
- [ ] 结尾有总结，可包含适度互动
- [ ] 段落过渡自然，逻辑连贯
- [ ] 技术内容准确无误
- [ ] 个人印记适度，不影响专业性
- [ ] 不使用 `[[toc]]`，使用 VitePress 自带目录导航
- [ ] 文章正文中不使用 emoji
- [ ] 不使用 `---` 作为章节分割线，依赖 VitePress 自动样式
- [ ] 提示、警告等内容使用 VitePress 自定义容器格式
- [ ] Frontmatter 包含 `layout: doc` 和 `lastUpdated: false`

## 常用语料库

**开头常用（南夏风格）:**
- "刚开始接触 XX 的时候，遇到了不少问题，整理出来分享给大家..."
- "相信很多人都遇到过 XX 的问题，我自己研究了一下，分享出来..."
- "刚从 JS 转到 TS 的时候，我看到 XX 这样的语法都是直接跳过的，心想..."
- "我发现很多人在做 XX 的时候，经常会 XX，但这样其实并不好，下面来说说原因..."

**过渡常用:**
- "说到这里，想起来当时踩的一个坑..."
- "可能有人会问，为什么要这样做呢？其实..."
- "我们一步一步来把这个问题弄清楚..."

**结尾常用:**
- "以上就是我对 XX 的一些理解，希望能帮到大家..."
- "其实 XX 这个东西，说难也难，说简单也简单，关键是..."
