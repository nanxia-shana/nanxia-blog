# 从 SPA 到 Diff：Vue 与 React

最早接触前端是在学校学习的时候，老师其实没有介绍过 SPA 这个概念。课堂上讲的还是传统的网页开发：HTML 页面、表单提交、点击链接整页刷新，服务器返回什么浏览器就显示什么。我真正开始接触单页面应用是在技术实验室自学的时候，那时候主流还是 Vue 2。

刚接触的时候最大的冲击是：页面跳转居然可以不刷新。点一下导航，地址栏变了，内容也换了，但浏览器顶部那个加载条一动不动。当时觉得这东西很神奇，也有点懵——不刷新，DOM 是怎么被换掉的？数据变了，页面又是怎么知道该更新哪里的？那时候只知道照着文档写 `data`、写模板，数据一变页面就跟着变，至于框架在背后做了什么，刚开始时我根本不理解。

后来用的框架多了，又冒出一个更具体的疑问：Vue 和 React 不都是单页应用吗，为什么 React 总要操心 `useMemo`、`useCallback` 这些性能优化的东西，而 Vue 好像默认就很快？

这个问题表面上在聊性能优化，其实背后牵扯到两件不同层级的事：一是 SPA 到底是什么，二是数据变化之后框架怎么把变化同步到页面上。第一件事 Vue 和 React 几乎一样，第二件事它们走了两条完全不同的路。

## 1. SPA 的本质是什么

要理解 Diff，得先理解 SPA 给前端带来了什么变化。

在传统的多页应用（MPA）里，浏览器和服务器的协作方式很简单：你点一个链接，浏览器发请求，服务器返回一整页新的 HTML，浏览器整页刷新。路由、渲染、状态这三件事基本都是服务器在管。

SPA 改变了这个模式。它第一次加载时通常只返回一个空的 HTML 外壳和一堆 JS，之后所有的页面切换、数据更新都在浏览器里完成，服务器退化成了只提供数据的接口。

| | 多页应用 MPA | 单页应用 SPA |
|---|---|---|
| 路由 | 服务器控制 | 客户端 JS 控制 |
| 页面切换 | 整页刷新 | 局部更新 |
| HTML 来源 | 每次请求服务器返回 | 初始一次，之后 JS 渲染 |
| 页面状态 | 跳转即丢失 | 保留在 JS 内存中 |
| 服务器职责 | 返回 HTML | 返回数据（API） |

换句话说，SPA 的本质是**用 JavaScript 接管了原本属于浏览器和服务器的三件事：路由、渲染、状态**。

这带来了流畅的体验，但也把一个责任甩给了框架：DOM 现在是 JS 在维护了，那么状态一变，页面该怎么更新？

最粗暴的办法是把整个容器 `innerHTML` 重写一遍。这在早期确实能用，但问题很明显，DOM 操作昂贵，整棵树重建会丢失输入焦点、滚动位置和子组件状态，性能也差。于是问题变成：**能不能只更新真正变化的那部分 DOM？**

虚拟 DOM 和 Diff 算法，就是框架为这个问题交出的答卷。而恰恰是在"怎么找到变化的部分"这件事上，Vue 和 React 给出了不同的答案。

## 2. 虚拟 DOM 和 Diff 在解决什么问题

虚拟 DOM 说白了就是用普通的 JavaScript 对象来描述真实 DOM。一个 `<div class="box">hello</div>`，在虚拟 DOM 里大概长这样：

```js
const vnode = {
  tag: 'div',
  props: { class: 'box' },
  children: 'hello'
}
```

状态变化后，框架会生成一棵新的虚拟 DOM 树，然后和旧的树进行比较，找出差异，最后只把差异对应的真实 DOM 更新掉。这个"比较两棵树找出差异"的过程，就是 Diff。

听上去很直白，但树的最小编辑距离在算法上是 O(n³) 的。n 稍微大一点就没法用了。所以所有主流框架都做了同一个关键妥协：**不做跨层级比较，只在同一层对比**。

这个妥协基于一个经验判断：在实际的 UI 开发中，元素很少在层级之间移动，变化大多发生在同层。于是复杂度从 O(n³) 直接降到了 O(n)。这也是 Diff 里常听到的"同层比较"原则。

在这个共同前提下，React 和 Vue 各自发展出了不同的更新哲学。

## 3. React：从根开始的递归调和

React 的思路可以概括为：**我不知道哪里会变，所以从触发更新的组件开始，把整棵子树重新走一遍。**

当你调用 `setState`（或者函数组件里的 setter），React 会从这个组件开始，重新调用它的渲染函数拿到新的虚拟 DOM，然后和旧的逐节点对比。这个过程叫 reconcile（调和）。

对比时它遵循三个简单的启发式规则：

- 节点类型不同，直接卸载重建（`<div>` 变成 `<span>`，整个子树都不要了）；
- 节点类型相同，就比较 props 和子节点；
- 列表子节点靠 `key` 来标识身份。

这套逻辑非常简洁、可预测，但它有一个直接后果：**一个组件状态变了，它下面整棵子树默认都会重新执行 render**，哪怕子组件的 props 根本没变。这就是为什么 React 给了你 `React.memo`、`useMemo`、`useCallback`——它们本质上是你在手动告诉 React"这个可以跳过"。

### Fiber 解决了什么

早期 React（15 及之前）的调和是递归的、一口气跑完的——从根组件开始，递归调用每一个子组件的 render，一旦开始就不能中断。如果组件树很大，这一口气可能要几十上百毫秒，浏览器这期间是单线程的，没法响应输入、没法跑动画、也没法绘制，用户就会觉得卡。

问题的根源在于：递归调用栈是 JS 引擎控制的，React 自己说了不算。React 16 引入的 Fiber 架构，本质上就是**重新实现了一个自己可以控制的"调用栈"**。

它把每个组件节点包装成一个 Fiber 节点，节点之间通过链表连接，记录了三个关系：

```text
child（第一个子节点）
sibling（右边的兄弟节点）
return（父节点）
```

有了这三个指针，React 就可以手动遍历整棵树，而不依赖 JS 的递归调用栈。遍历顺序是深度优先的：先深入子节点，子节点处理完了再回到兄弟节点，兄弟都处理完了再回到父节点。

```text
App
└─ TodoList
   ├─ input        （先走 child）
   ├─ TodoItem ①  （再走 sibling）
   ├─ TodoItem ②
   └─ TodoItem ③
```

关键在于：因为遍历是 React 自己驱动的，它可以在处理完任意一个 Fiber 节点后**停下来**，看看手头有没有更紧急的事（比如用户输入、动画帧），有就先把主线程让出去，等浏览器忙完了再从上次停下的地方接着遍历。每个 Fiber 节点就是一个最小工作单元，这就是"可中断"的含义。

这也是 React 并发能力的基础。它不直接让 Diff 变快（该比的节点还是要比），但让 Diff **可以被打断、被按优先级调度**，从而让页面保持响应。理解这一点很重要：React 的更新策略是"深度优先、可中断、可调度"，它优先保证交互流畅，而不是一口气算完。

::: tip 小提示
`React.memo` 并不是万能的。它本身也要做 props 比较，浅比较也有成本。只给那些确实重、且经常以相同 props 渲染的组件加，别一上来全项目包裹。
:::

## 4. Vue：响应式驱动的靶向更新

Vue 走的是另一条路：**我知道哪里会变，所以只更新那里。**

它的底气来自响应式系统。在 Vue 3 里，`reactive` 包裹的对象会被 `Proxy` 代理，`ref` 包裹的值则通过 getter/setter 拦截（对象类型的 `.value` 内部还是会转成 reactive）。组件渲染时会收集依赖——"这个组件用到了哪些字段"。当这些字段变化时，只有依赖它们的组件才会被通知更新，其他组件根本不会被触发。

所以 Vue 的更新粒度天然更细，不是从某个根开始全树遍历，而是精确到受影响的组件。

但 Vue 真正拉开差距的地方在编译器。React 基本上是把 JSX 当运行时的东西，编译时不做太多分析；而 Vue 的模板编译器会在构建时做大量优化，其中有三个特别关键：

**静态提升。** 模板里不随状态变化的节点，编译器会把它们提到渲染函数外面，每次更新直接复用，不需要重新创建虚拟 DOM，也不会进入 Diff。

**PatchFlag。** 对于会变化的节点，编译器会标记它具体是哪部分变了——是文字内容、是 class、还是 props。Diff 的时候不用把整个节点所有属性都比一遍，只看标记的那一位就行。

**Block。** 编译器会把一个模板里的动态节点收集成一个扁平数组（block），Diff 时直接遍历这个数组，而不用再递归整棵树。静态节点被跳过了，树的层级也被拍平了。

这三招合起来，让 Vue 的 Diff 更像"靶向打击"：编译时就已经知道哪些节点是动态的、动态在哪里，运行时只需要精准对比这些地方。

在子节点的列表 Diff 上，Vue 3 还采用了最长递增子序列算法。简单说，当列表顺序变化时，它能找出那些"位置虽然不同但可以原地复用"的节点，只移动真正需要移动的，把 DOM 操作降到最少。这块内部实现比较精巧，但日常开发里你能感知到的就是——只要 `key` 写对，长列表的重排会比较高效。

::: info 关于 Vue 2
Vue 2 用 `Object.defineProperty` 实现响应式，受限于语法无法监听属性新增和数组下标变化，需要 `Vue.set` 之类的 API 兜底。Vue 3 换成 `Proxy` 后这些问题基本消失，编译器优化也更激进。如果你还在维护 Vue 2 项目，这些差异值得留意。
:::

## 5. 同一个例子，两种 Diff

前面分开讲了 React 和 Vue 的思路，这一节用一个完全相同的交互场景，把两边的更新过程并排走一遍。

场景很简单：一个输入框加一个待办列表，在输入框里打字，列表会按关键词筛选。这个交互同时包含了"文本变化"和"列表增删"，正好能覆盖 Diff 最常处理的两类更新。

React 版本的骨架大概是这样：

```jsx
function TodoList() {
  const [keyword, setKeyword] = useState('')
  const [todos] = useState([
    { id: 1, title: '写文档' },
    { id: 2, title: '改 bug' },
    { id: 3, title: '写单元测试' },
  ])

  const visible = todos.filter(t => t.title.includes(keyword))

  return (
    <>
      <input
        value={keyword}
        onChange={e => setKeyword(e.target.value)}
      />
      {visible.map(todo => (
        <TodoItem key={todo.id} todo={todo} />
      ))}
    </>
  )
}
```

Vue 版本的骨架如下：

```vue
<script setup>
const keyword = ref('')
const todos = ref([
  { id: 1, title: '写文档' },
  { id: 2, title: '改 bug' },
  { id: 3, title: '写单元测试' },
])
const visibleTodos = computed(() =>
  todos.value.filter(t => t.title.includes(keyword.value))
)
</script>

<template>
  <input v-model="keyword" />
  <TodoItem
    v-for="todo in visibleTodos"
    :key="todo.id"
    :todo="todo"
  />
</template>
```

代码长得很像，做的事也一样。但当你在输入框里敲下一个字，两边背后发生的事差别很大。

### React 这边发生了什么

我们一步一步追。假设用户在输入框里敲下了"写"这个字。

::: tip 第一步
`onChange` 触发，调用 `setKeyword('写')`。React 收到状态更新请求，它不会立刻改 DOM，而是把这次更新排进一个调度队列，等当前事件处理完，再统一开始工作。
:::
::: tip 第二步
React 从触发更新的组件——也就是 `TodoList`——开始，**把整个组件函数从头执行一遍**。`useState` 返回新的 keyword 值，`visible` 重新 filter 一遍，JSX 里的 `visible.map(...)` 重新跑一遍，最终生成一棵全新的虚拟 DOM 树。这一步里，你写在函数体里的所有逻辑都会重新执行，不管它和这次更新有没有关系。
:::
::: tip 第三步
进入 reconcile（调和）阶段。React 拿着新生成的虚拟 DOM 树，和上一次的旧树做对比，从 `TodoList` 的根节点开始，一层一层往下走。它看到了一堆 `<TodoItem>`，但它事先并不知道这些子组件有没有变，所以默认会逐个去比较它们的 props：新的 todo 是什么、旧的 todo 是什么、引用是不是同一个。
:::
::: warning *注意*
这里是关键。对比完 props 之后，如果一个 `TodoItem` 的 props 引用全都没变，**React 默认仍然会继续往下调和它的子树、重新执行它的渲染逻辑**，因为 React 的契约是"状态变了就重新渲染，子树默认跟着走"。它不会替你做"props 没变就跳过"这个判断——除非你用 `React.memo` 把组件包起来，显式告诉它"props 浅比较相等就别重新渲染了"。这就是为什么 React 项目里到处能看到 `memo`、`useMemo`、`useCallback`，它们本质上都是在帮 React 做它默认不做的"跳过"判断。
:::
::: tip 第四步
处理筛选带来的节点增删。上一次有三个 `TodoItem`（id 1、2、3），这一次因为 keyword 变成了"写"，`visible` 只剩两个（id 1 和 3，"改 bug" 被过滤掉了）。React 根据 `key` 发现：id 为 2 的节点在新树里找不到了，于是卸载它；id 为 1 和 3 的节点在新树里还在，继续保留，但它们默认还是会走一遍上面说的重新渲染流程。
:::
::: tip 第五步
调和结束，React 进入 commit 阶段，把这一轮算出的所有 DOM 变更（删掉一个节点、更新 input 的 value 等）一次性提交给真实 DOM，然后浏览器绘制。
:::

整个过程可以概括成：**状态变了 → 整棵子树重新算一遍 → 逐节点 Diff → 提交差异**。React 把"哪些该跳过"的判断留给了开发者。

### Vue 这边发生了什么

同样是敲下"写"这个字，Vue 这边的路径很不一样。还是一步一步看。

::: tip 第一步
`<input v-model="keyword">` 让输入和响应式数据双向绑定。你输入一个字，Vue 会把新值赋给 `keyword.value`。`keyword` 是一个基本类型的 ref，底层通过 getter/setter 拦截 `.value` 的读写（对象类型的 ref 才会在内部用到 Proxy），赋值动作会触发它的 setter。
:::
::: tip 第二步
Vue 顺着依赖关系往外通知。首次渲染时，Vue 已经建立好了一张依赖图：`visibleTodos` 这个计算属性读取过 `keyword`，所以它是 `keyword` 的依赖者；组件的渲染 effect（真正执行模板编译后渲染函数的那个函数）又读取过 `visibleTodos`，所以它是 `visibleTodos` 的依赖者。setter 一触发，Vue 就沿着这张图，只通知真正依赖 `keyword` 的那部分。和这次输入无关的组件、数据，根本不会被叫醒。
:::
::: tip 第三步
`visibleTodos` 被标记为"脏"，组件的渲染 effect 被调度执行，重新生成虚拟 DOM。注意这里和 React 的区别：不是"组件函数从头跑一遍、所有子节点重新算"，而是运行时带着编译器给的"地图"去更新。
:::
::: tip 第四步
这个"地图"是重点——**编译器在构建时就分析过模板**。它编译这段模板时能看出：

- `<input>` 的 value 绑定了 `keyword`，这是一个动态属性绑定，会给它打一个 PatchFlag，标记"这个节点的 props 会变"；
- `v-for` 渲染出来的列表是一个动态区块，会被收集成一个 Block；
- 模板里没有其他响应式绑定的结构是静态的（比如写死的标签、固定的文本和属性），这些节点会被"静态提升"——渲染函数第二次执行时直接复用同一个虚拟节点，连新建对象都省了。
:::
::: tip 第五步
进入运行时 Diff 时，Vue 不需要从根节点开始递归整棵树。它直接拿到这个组件的 Block——一个扁平的动态节点数组，里面只有 input 和 v-for 列表这些真正会变的东西。Diff 只在这些动态节点之间进行，静态节点连比较都省了。
:::
::: tip 第六步
处理 `<TodoItem>` 子组件。每个 `TodoItem` 接收一个 `todo` prop。筛选前后，保留下来的"写文档"和"写单元测试"这两项，它们的 `todo` 对象引用完全没变。Vue 的响应式系统发现这个子组件的 props 引用没变、自身的依赖也没被触发，就**直接跳过这个子组件的重新渲染**，连它的渲染函数都不会执行。被过滤掉的"改 bug"对应的节点，因为在新的 Block 里找不到了，才会被卸载。
:::
::: tip 第七步
和 React 类似，Vue 把算出的 DOM 差异提交给真实 DOM。但走到这一步时，它实际需要做的工作已经少得多。
:::
整个过程可以概括成：**数据变了 → 沿依赖图通知 → 编译器标记的动态节点才参与 Diff → 没变的子组件直接跳过**。"哪些该跳过"这件事，Vue 大部分时候替你做了。

回过头看，两边工作量的差距其实都集中在"保留下来的子组件怎么处理"上：React 默认让它们跟着重新渲染，等你用 `memo` 去拦；Vue 发现 props 引用没变就直接跳过。这也正是开头那个问题的答案——React 之所以总在谈 `useMemo`、`memo`，是因为"哪些该跳过"这件事它默认交给了你。

### 如果列表顺序被打乱

再看一个场景：把列表顺序随机打乱。这时候两边都依赖 `key` 来识别"哪个节点是哪个"，但具体策略不同。

React 的做法是基于 key 找到可复用的节点，然后逐个对比、移动。Vue 3 在这个基础上用了最长递增子序列：在新旧顺序里找出一段"相对位置完全不变"的节点，这些保持不动，只移动其余的。节点多的时候，这种方式能少做几次 DOM 移动。

日常开发里你不太会直接感知到这个差异，但当列表很长、重排很频繁时，它会实实在在地影响操作的流畅度。当然，这一切的前提都是 `key` 要写对——用数组下标当 key 时，两边都会因为节点身份错乱而出现状态串台的 bug。

## 6. Vue 与 React 的差异

把前面的内容收拢一下，核心差异其实就这张表：

| | React | Vue |
|---|---|---|
| 更新触发 | 调用 setState，从该组件重新渲染 | 响应式依赖被修改，通知对应组件 |
| 更新范围 | 整棵子树递归调和 | 靶向更新受影响组件 |
| 编译时优化 | 几乎没有，JSX 运行时处理 | 静态提升、PatchFlag、Block |
| Diff 方式 | 同层比较 + Fiber 可中断调度 | 动态节点收集 + 靶向比对 |
| 列表复用 | key 协调 | key + 最长递增子序列 |
| 心智模型 | Pull（我重新算一遍，你告诉我变没变） | Push（数据变了我精确推到对应位置） |
| 性能抓手 | memo/useMemo/useCallback | 大部分情况框架默认处理 |

最值得体会的是最后一行的差别。React 把"要不要跳过更新"这件事部分交给了你，所以你需要理解渲染机制、合理使用记忆化；Vue 把这件事收进了响应式和编译器里，默认就做了很多。这不是谁优谁劣，而是取舍——React 用更多的手动控制换来了调度上的灵活性（并发、Suspense、服务端组件这些能力都建立在 Fiber 之上），Vue 用编译时的投入换来了更省心的默认性能。

## 7. 对实际开发的影响

原理听起来很远，其实每天写代码都在受它影响。

**关于 key。** 上一节已经讲过 key 在 Diff 里的作用，落到代码上，最常见的错误就是图省事用数组下标做 key。列表会插入、删除、排序时，下标会跟着变，但它代表的数据已经换了，框架却以为节点没变，结果就是输入框内容串台、动画错乱。这个坑我自己踩过，排查了半天才意识到是 key 的问题。

```js
// 列表会变动时不要这样写
{items.map((item, index) => <Row key={index} />)}

// 用数据本身的稳定 id
{items.map(item => <Row key={item.id} />)}
```

**关于 React 的记忆化。** 很多人刚写 React 会到处加 `useMemo`、`useCallback`，以为加了就快。实际上它们不是免费的，而且大部分组件根本不重。真正值得优化的是那些渲染昂贵、引用相等敏感（比如被用在 useEffect 依赖里、或传给 memo 子组件）的值。与其无脑加，不如先装个 React DevTools 看哪些组件真的在频繁重渲染。

**关于 Vue 的"省心"。** Vue 默认性能好不等于可以乱来。一个组件绑定了一个巨大的响应式对象、或者模板里写了复杂的计算（尤其是在 `v-for` 里调用方法），一样会卡。响应式让你不用手动优化，但该抽计算属性、该分页的大列表还是要做。

::: danger 踩坑提醒
不要在 React 的渲染函数里直接修改对象或数组、不要在 Vue 的模板里调用会产生副作用的方法。Diff 过程可能多次执行渲染，副作用放进去会出现难以复现的 bug。这类问题排查起来非常头疼。
:::

## 写在最后

回到开头那个问题：Vue 和 React 同为 SPA，为什么性能上的体感不同？

因为 SPA 只规定了"用 JS 接管路由、渲染和状态"这件事，但接管之后怎么把数据变化同步到 DOM，框架是有自由的。React 选择了一条更通用、更灵活、但需要你理解调度和记忆化的路；Vue 选择了一条更内敛、默认更省心、但把大量工作交给编译器的路。

理解了这层区别，再去看两边的生态和最佳实践，很多事情就说得通了：为什么 React 总在谈并发渲染、为什么 Vue 的模板总比 JSX 多一些"魔法"、为什么它们的性能优化指南写得完全不一样。

工具没有绝对的好坏，关键是知道它在底层替你做了什么、又把什么留给了你。希望这篇文章能帮你把这层窗户纸捅破，大家早点下班。
